0. 범위 확정·착수 조건 · 예정
담당: 사용자 / 개발 담당
할 일: 이번 요청은 설명과 문서 작성까지 확정. 후속 구현의 첫 범위는 상품 화면 한 개로 제안.
통과 기준: 상품 필드·서버 선택·검증 기준이 합의됨.
실패 대응/범위: evol 전용 승인 파일 생성은 MIMO 문서 작성 조건이 아님. 후속 구현은 아직 미착수.
1. 화면만 가져오기 · 예정
담당: 프런트엔드
할 일: 기본 요소로 상품 카드 manifest 구성 → 형식 검사 → 새 프로젝트로 가져오기.
통과 기준: 문구·색상·순서를 바꾼 뒤 저장·다시 열어도 유지.
실패 대응/범위: 알 수 없는 type 또는 누락 자산이면 패키지 수정. 가져오기 성공과 API 동작을 구분.
2. 상품 조회 연결 · 예정
담당: 백엔드 + 프런트엔드
할 일: 조회 계약 확정 → 업무 API 구현 → hydrator 호출과 결과 반영 연결.
통과 기준: 실제 시험 DB 상품이 보이고 빈 목록·오류·시간초과도 구분됨.
실패 대응/범위: 모의 데이터에만 성공하면 완료 아님. 잘못된 응답은 표시하지 않고 재시도 안내.
3. 업무 데이터 저장 · 예정
담당: DB + 백엔드
할 일: 리뷰·장바구니·주문 테이블과 migration, 권한, 트랜잭션, 중복 요청 처리.
통과 기준: 다시 접속해도 저장 유지. 다른 사용자 데이터 접근 거부. 재전송해도 중복 주문 없음.
실패 대응/범위: 서버 로그와 제약 위반 원인 확인. 기존 Firebase에서 단계 전환하고 대조.
4. 카메라 기능 연결 · 예정
담당: 프런트엔드 + AI 백엔드
할 일: 기존 오류 정리 → 권한·촬영 → 업로드 → 추론 → 결과 표시.
통과 기준: 권한 거부·카메라 없음·큰 파일·추론 실패와 성공을 모두 처리.
실패 대응/범위: 서버 부재 시 버튼 비활성/안내. 미리보기에서는 실제 촬영·업로드하지 않음.
5. 시험 배포·사용자 검수 · 예정
담당: 개발 담당 + 사용자
할 일: 테스트 환경 배포 → 고정 화면 버전과 실제 동작 확인 → 결과 보고.
통과 기준: 편집기·공개 화면·실제 API 값 일치, 모바일 확인.
실패 대응/범위: 화면 구성은 이전 릴리스로 복구. 서버·DB는 별도 배포 이력/호환 migration으로 복구. 운영 배포 SHA는 미확인.
