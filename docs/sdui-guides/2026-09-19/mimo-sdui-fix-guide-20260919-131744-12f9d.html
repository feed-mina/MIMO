3-2. 두 가지 재사용 경로

A · 기존 요소 조합(첫 단계 권고): MIMO → 화면/데이터/동작 분해 → Card·Image·Text·Grid로 manifest 작성 → 파일 가져오기 검사 → 새 프로젝트 저장. 화면 전체 템플릿 가져오기와 “요소 팔레트에 상품 카드 버튼 추가”는 다릅니다. 반복 사용할 묶음은 별도 프리셋 삽입 UI를 추가해야 합니다.

B · 전용 요소/플러그인: MimoProductList·MimoMakeup 같은 이름은 신규 제안이며 현재 type으로 바로 넣으면 안 됩니다. 요소 등록·기본값·속성 편집·검증·정적 미리보기·공개 렌더러를 함께 확장합니다. React Studio도 사용한다면 CanvasPanel.jsx에 같은 표현을 구현합니다. React 부품을 보존할 경우 의존성을 묶은 mount/unmount 어댑터와 CSS 격리가 필요합니다.

[확인] plugin 계약은 actions(실행), hydrators(조회), widgets(복합 화면)를 구분합니다. [추측: 권고] 등록 후 조회 결과를 어느 노드에 반영할지, widget을 언제 mount/unmount할지, 오류를 어디에 표시할지 구현하세요. source.widgetId나 refDataId를 적는 것만으로 자동 연결되지 않습니다. 공개 부트스트랩은 모듈의 createPluginRegistry와 검증 범위가 같지 않으므로 서버에서 권한·입출력 검증을 반드시 수행합니다.

3-3. “스키마”는 세 종류입니다

종류내용소유자

OpenAPI의 상품 응답 모델에서 입력 폼 초안을 만들 수는 있지만, 레이아웃·브랜드 디자인·업무 권한이 자동으로 완성되지는 않습니다. UI metadata와 검증·미리보기를 별도로 둡니다. API 모델과 DB 엔티티도 그대로 노출하지 않고 응답 DTO를 분리합니다.

3-4. Spring Boot와 FastAPI 중 무엇을 써도 SDUI가 가능한가?

선택담당 방식적합한 조건
FastAPI 단독Pydantic 입출력 모델 → 서비스 → DB; JSON 응답과 OpenAPIPython 중심으로 상품·리뷰 MVP부터 만들 때 단순. 추론이 무거우면 별도 작업 프로세스/큐.
Spring Boot 단독Controller → DTO 검증 → Service → Repository → DBJava 운영 경험과 거래·업무 로직이 중심일 때. JSON으로 같은 계약 제공.
Spring Boot + FastAPISpring은 주문·사용자·업무 DB, FastAPI는 AI 추론 API두 서비스를 운영할 이유가 있을 때만. 양쪽에서 같은 주문 테이블을 직접 수정하지 않음.

[추측: 권고] 현재 저장소에는 재사용할 Spring 서버가 확인되지 않았으므로, Python 경험이 있다면 FastAPI 한 개로 상품 조회부터 시작하는 안이 단순합니다. 이미 운영 중인 Java 서버가 별도로 있다면 Spring을 유지하고 AI만 분리하세요. 이것은 성능 우열 판단이 아닌 개발 범위 선택입니다.

[확인] 현재 runtimeAdapters 허용값은 cloudflare-worker-static·react-next입니다. 여기에 spring-boot/fastapi를 추가하는 대신, 브라우저 플러그인에서 해당 서버의 HTTP API를 호출합니다. 서버는 별도 호스팅이 필요하며 Studio 게시가 Spring/Python 서버를 함께 배포하지 않습니다.

3-5. 제안 API 계약

경로 (신규 제안)입력 → 출력구현 기준
GET /api/mimo/products목록 조건·페이지 → {items:[{id,title,priceMinor,currency,imageUrl}],nextCursor}신규 제안. 구 /itmes 노드명과 imgUrl→imageUrl 변환은 어댑터 책임.
POST /api/mimo/cart/items{productId,quantity} → 서버가 계산한 cart신규 제안. 인증 주체로 사용자 결정, 양수 수량·존재 상품 검증.
POST /api/mimo/reviews{productId,rating,content,assetId?} → review신규 제안. 저장 성공 후 같은 조회 API로 목록 갱신.
POST /api/mimo/orders{cartId,idempotencyKey} → order신규 제안. 서버가 재고/금액 재검사, 트랜잭션+중복 키 처리.
POST /api/mimo/assetsmultipart 사진 → {assetId}신규 제안. 객체 저장소 사용, 형식·크기·접근 주체 검사.
POST /api/mimo/simulations{assetId,feature,color} → 202 {jobId,status}신규 제안. GET /api/mimo/simulations/{id}로 진행/완료/실패 조회. 기존 localhost 계약과 구분.

아래는 장바구니 입력 JSON Schema의 제안 예시입니다. 실제 상품 존재·사용자 권한·재고는 이 타입 검사 외에 서버가 검사합니다. 예시 수량 상한은 99개이며 실제 업무 기준으로 확정해야 합니다.

{
  "type": "object",
  "required": [
    "productId",
    "quantity"
  ],
  "additionalProperties": false,
  "properties": {
    "productId": {
      "type": "string",
      "minLength": 1
    },
    "quantity": {
      "type": "integer",
      "minimum": 1,
      "maximum": 99
    }
  }
}

Button의 source.actionType = "mimo.cart.add"는 제안 operation 이름입니다. page.pluginRefs와 plugins.provides.actions에 선언하고, entry 파일 구현을 등록해야 합니다. 현행 공개 버튼 브리지는 {form:{…}}을 전달하므로 어댑터에서 productId·quantity로 변환합니다. events.onClick의 기본 action은 setState·toggleState·navigate뿐이므로 임의의 apiCall을 넣지 않습니다.

API 서버 주소는 환경 설정/허용 목록에서 관리합니다. 가능하면 같은 출처의 /api/mimo 경유로 연결하고, 직접 호출한다면 HTTPS·CORS·쿠키/토큰 정책을 맞춥니다. 내부 DB 접속 정보·비밀 키·토큰을 화면 manifest에 넣지 않습니다. 일반 조회 실패와 인증 만료를 구분합니다.

3-6. 업무 DB 설계안과 관계

테이블 (신규 제안, 마지막 행 제외)키·관계책임
products / product_variantsproducts.id PK; variants.product_id FK → products.id; UNIQUE(product_id,sku)상품과 색상·SKU·판매가를 분리. 금액은 최소 화폐 단위 정수, 통화 코드 저장.
users / reviewsusers.id PK; reviews.user_id FK; reviews.product_id FK인증 공급자 subject는 UNIQUE. rating 범위와 본문 길이 제약. 로그인은 검증된 공급자 유지 가능.
carts / cart_itemscarts.user_id FK; items.cart_id FK; items.variant_id FK; UNIQUE(cart_id,variant_id)장바구니 상태와 수량. 클라이언트 총액은 확정 금액이 아님.
orders / order_itemsorders.user_id FK; order_items.order_id FK; UNIQUE(user_id,idempotency_key)주문 당시 상품명·단가·통화 스냅샷. 주문 합계와 재고 변경은 트랜잭션.
media_assets / simulation_jobsassets.owner_id FK; jobs.owner_id FK; jobs.input_asset_id FK; output_asset_id FK nullable사진의 object key, 만료·삭제 정책. 작업 상태 queued/running/succeeded/failed 및 오류 코드.
Studio D1 (기존)studio_projects / studio_project_versions / studio_releases화면 manifest와 버전·공개본 저장. 업무 DB를 교체하는 것이 아님.

정확한 관계: products 1:N product_variants, users 1:N reviews, products 1:N reviews, users 1:N carts, carts 1:N cart_items, product_variants 1:N cart_items, users 1:N orders, orders 1:N order_items, users 1:N media_assets, media_assets 1:N simulation_jobs(input). 이는 제안 ERD이며 기존 Firebase에 이러한 외래키가 존재한다고 확인한 것은 아닙니다.

업무 DB는 PostgreSQL 또는 MySQL처럼 관계·트랜잭션을 지원하는 DB를 선택할 수 있습니다. 처음부터 Firebase 전체를 옮길 필요는 없습니다. 서버 어댑터로 기존 데이터를 읽어 계약을 고정한 뒤, 상품 → 리뷰 → 주문 순서로 이전하며 건수·키·금액·사용자 연결을 대조하세요. SQL 테이블 생성은 별도 migration 실행이 필요합니다. manifest를 가져온다고 DB가 만들어지지 않습니다.

3-7. 세 가지 버전을 구분

manifest의 schema/documentVersion·template version, API contract version, DB migration version은 각각 관리합니다. 공개 화면은 검증된 manifest 버전을 고정하고, 서버는 그 화면이 요구하는 API 계약을 유지합니다. DB 변경은 먼저 호환 필드 추가 → 데이터 전환 → 구버전 사용 종료 순서로 진행합니다.

공식 기술 근거

FastAPI 응답 모델은 응답 검증·문서 생성을 설명하고, Spring REST 안내는 JSON 서비스 구현을 설명합니다. JSON Schema object 규칙은 필수·추가 필드 제어 근거입니다. 위 MIMO 구조와 선택 권고는 이를 적용한 설계안입니다.

6. 개발 플로우와 통과 기준

[계획] 아래는 후속 구현 순서입니다. 현재 완료된 것은 조사·문서·샘플 검사이며, 운영 승인이나 배포 완료를 의미하지 않습니다. evol 스킬의 0번 승인 게이트는 이 프로젝트의 범위 확정 단계로 옮겼습니다. 회사 전용 승인 파일·랩 배포 명령은 적용 대상이 아닙니다.

0. 범위 확정·착수 조건 · 예정

담당: 사용자 / 개발 담당

할 일: 이번 요청은 설명과 문서 작성까지 확정. 후속 구현의 첫 범위는 상품 화면 한 개로 제안.

통과 기준: 상품 필드·서버 선택·검증 기준이 합의됨.

실패 대응/범위: evol 전용 승인 파일 생성은 MIMO 문서 작성 조건이 아님. 후속 구현은 아직 미착수.

1. 화면만 가져오기 · 예정

담당: 프런트엔드

할 일: 기본 요소로 상품 카드 manifest 구성 → 형식 검사 → 새 프로젝트로 가져오기.

통과 기준: 문구·색상·순서를 바꾼 뒤 저장·다시 열어도 유지.

실패 대응/범위: 알 수 없는 type 또는 누락 자산이면 패키지 수정. 가져오기 성공과 API 동작을 구분.

2. 상품 조회 연결 · 예정

담당: 백엔드 + 프런트엔드

할 일: 조회 계약 확정 → 업무 API 구현 → hydrator 호출과 결과 반영 연결.

통과 기준: 실제 시험 DB 상품이 보이고 빈 목록·오류·시간초과도 구분됨.

실패 대응/범위: 모의 데이터에만 성공하면 완료 아님. 잘못된 응답은 표시하지 않고 재시도 안내.

통과 기준: 다시 접속해도 저장 유지. 다른 사용자 데이터 접근 거부. 재전송해도 중복 주문 없음.

실패 대응/범위: 서버 로그와 제약 위반 원인 확인. 기존 Firebase에서 단계 전환하고 대조.

4. 카메라 기능 연결 · 예정

담당: 프런트엔드 + AI 백엔드

할 일: 기존 오류 정리 → 권한·촬영 → 업로드 → 추론 → 결과 표시.

통과 기준: 권한 거부·카메라 없음·큰 파일·추론 실패와 성공을 모두 처리.

실패 대응/범위: 서버 부재 시 버튼 비활성/안내. 미리보기에서는 실제 촬영·업로드하지 않음.

담당: 개발 담당 + 사용자

통과 기준: 편집기·공개 화면·실제 API 값 일치, 모바일 확인.

실패 대응/범위: 화면 구성은 이전 릴리스로 복구. 서버·DB는 별도 배포 이력/호환 migration으로 복구. 운영 배포 SHA는 미확인.
